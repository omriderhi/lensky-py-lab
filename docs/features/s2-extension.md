# Sentinel-2 series: one product, extended to Nov 2021 (decision record for the paper review)

## Decision

`data/research_results/RH_NDVI/S2.csv` is **regenerated entirely** from
`COPERNICUS/S2_SR_HARMONIZED` with the research script's settings, for 2019-01-01 to 2021-12-05
(107 images, last image 2021-11-16). Run `python scripts/pull_s2_gee.py --project <gee-project>` to
reproduce it. Earlier versions of this branch appended new images to the old export; that mixed
processing versions and was replaced.

**Why**
1. The old export mixes Sentinel-2 processing baselines with what Earth Engine serves
   now: 47 of its 79 comparable dates differ from the current archive by up to 0.10 NDVI (RMSE 0.029,
   mean +0.005, r = 0.976). All of them are baseline 05.00; every baseline 02.xx date matches
   exactly. Reprocessing by ESA after the export is the likely cause (not verified).
2. The collection the research script used (`COPERNICUS/S2_SR`) is deprecated, now returns 74 images
   instead of 135 for the same filter, and carries the +1000 reflectance offset on baseline 05.00
   scenes (NDVI about 0.41 where harmonised gives about 0.69). It cannot reproduce or continue the
   series.
3. Appending to the old rows would put baseline 05.00 data after 2021-04-30 on top of older baselines
   before it. One query, one collection, one processing state avoids that seam, and the series can be
   regenerated by anyone with the script.

**Cost.** Published S2 values change slightly (59 of 106 dates identical to 3 decimals, RMSE 0.025
over all shared dates). The date set is unchanged (the same 107 dates; 12 old rows were empty
fully-masked images, and 2019-08-14 now has a value). The original file is in git history
(`data/research_results/RH_NDVI/S2.csv` at commit `ef914c2`).

## Settings (match the research JS)

| Item | Original JS | Now |
|---|---|---|
| Collection | `COPERNICUS/S2_SR` (deprecated) | `COPERNICUS/S2_SR_HARMONIZED` |
| Cloud filter | `CLOUD_COVERAGE_ASSESSMENT < 10` | same |
| NDVI / mask | `(B8-B4)/(B8+B4)`, keep `>= 0.35` | same |
| Reducer | mean, scale 10, point 34.946667 E / 32.555806 N | same (`bestEffort=True`) |
| Window | 2018-01-01 .. 2022-09-01 | 2019-01-01 .. 2021-12-05 (start unchanged from the old CSV; end = last NSRS date 2021-11-04 + 1 month) |

`GEEClient` and a literal port of the JS logic on the harmonised collection return identical series
(135 images over 2018-01-16 to 2021-11-16, max difference 0.0). `CLOUD_COVERAGE_ASSESSMENT` (L1C
tile metadata) and `CLOUDY_PIXEL_PERCENTAGE` (L2A) are tile-wide and correlate at 0.999 here; they
select different images only on 2018-03-12 and 2018-03-17, outside the S2 record. Using the script's
property reproduces the script; it is not a correctness fix. Pixel values are not corrected for
sub-tile cloud at the point: the filter is scene-level only.

## For the reviewer: what to state and what not to claim

- State that S2 is `S2_SR_HARMONIZED` (surface reflectance, scene-level cloud filter < 10 %, NDVI >= 0.35),
  not `S2_SR`.
- The S2 start of season is the least stable marker: it moved 25 days (2019-11-05 to 2019-11-30) when
  the product version and the record length changed. Do not quote S2 SoS to the day.
- The S2 2019 season starts at 2018-12-31/2019-01-01 (SoS and PoS are edge artefacts).
- The floor of 0.08 was chosen on the old S2 series; it was re-audited on the regenerated series (below). Say
  that with this floor the S2 outlier filter removes 1 of 91 observations, i.e. S2 is effectively unfiltered
  apart from the extreme-value limit and LOWESS. Do not describe S2 as having been "cleaned of outliers".
- MODIS and L8 were not re-checked against the JS (the JS uses scale 10 for all sources, `MODIS/006`
  and `LANDSAT/LC08/C01`; the client uses `MODIS/061` and Landsat C02).

## Outlier floor re-audit on the single-product series

`python scripts/audit/s2_floor_reaudit.py` (outputs in `data/results/s2_floor_reaudit/`, gitignored).
S2 has 91 valid observations after the extreme-value filter (min 0.4). Window 7, k 3:

| Floor | Removed (below / above local median) | PoS value 2019 / 2020 / 2021 | RMSE vs NSRS mean (n = 46 overlap) |
|---|---|---|---|
| none | 0 | 0.744 / 0.704 / 0.810 | 0.059 |
| 0.02 (default) | 14 (4 / 10) | 0.711 / 0.685 / 0.812 | 0.059 (n = 40) |
| 0.04 | 10 | 0.711 / 0.685 / 0.812 | 0.061 |
| 0.06 | 3 | 0.744 / 0.702 / 0.810 | 0.059 |
| **0.08 (used)** | **1** | **0.744 / 0.702 / 0.810** | 0.059 |
| 0.10 / 0.12 / 0.15 | 1 | identical to 0.08 | 0.059 |

- The default floor 0.02 removes real high-season values (2018-12-31 0.744, 2020-01-10 0.712, 2020-03-15 0.713),
  moves the 2020 PoS date from day 64 to day 36 and the 2019 PoS from an edge artefact (day 365) to day 40.
  The original finding is confirmed on the new series.
- Floors 0.08 to 0.15 give identical results; 0.06 is within 0.002 of them on peak values. The choice of 0.08
  inside that range is not tuned to one value.
- At 0.08 the only point removed is 2019-07-14 (0.646 against a local median of 0.472, an isolated summer
  spike). It lies before the NSRS record (starts 2019-10-06), so NSRS cannot validate the removal; agreement
  with NSRS is the same with and without the filter. The point was not inspected in the imagery.
- Window matters more than floor: window 11 or 15 with floor <= 0.08 removes 7-11 observations and cuts the
  2020 PoS value to 0.561; they need floor 0.15 to recover (0.684). Window 5 behaves like 7.
  The result is therefore conditional on window = 7 observations (about 5 weeks for S2).
- SoS and EoS dates are stable across floors >= 0.06 (SoS 2020 day 334, EoS 2020 day 150). The 2020 SoS is the
  same with no filter (day 334), so its 25-day move versus the old series comes from the data version, not
  the filter.
- Not verified: other window / k combinations beyond window 5-15 and k = 3 (k was not varied here).
